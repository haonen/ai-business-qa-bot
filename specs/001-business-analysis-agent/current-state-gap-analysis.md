# Current-State Gap Analysis: backup 线上版本为什么难用、分析不够聪明

**Baseline**: `backup/server-20260831-164408` at commit `a86d868`

**Compared against**: [spec.md](./spec.md)

**Method**: 对提交快照做静态数据流追踪，从用户问题依次检查路由、任务规划、查询链、跨域组合、结论生成、会话上下文与测试覆盖。当前工作区包含正在进行的路由调试改动，本报告只以提交快照为正式证据；由于没有纳入线上对话日志或具体失败问题，报告判断的是架构性根因，不能量化每类问题在线上的实际发生频率。

## Executive Conclusion

当前版本并不是一个围绕业务问题自主工作的分析 Agent，而是一个带有大量业务口径保护的**模板路由与报告生成系统**。

它的主要优化目标是：

1. 把问句分到正确的报告类型；
2. 用固定 Tool 和固定顺序查询数据；
3. 用确定性模板稳定出表；
4. 限制模型超出证据或产生因果幻觉。

而目标产品要求的是：

1. 理解用户真正要做的业务判断；
2. 从可拆分的内部分析方法中动态选择最小充分证据；
3. 根据结果继续筛查和下钻；
4. 跨生意与媒体证据形成统一解释；
5. 给出有证据的业务含义、机会/风险、行动方向和验证建议。

因此，当前体验问题的第一根因是**产品架构目标错位**。路由 bug 和模型能力会放大问题，但不是全部根因。仅把千问换成 GLM 5.2，可以改善意图抽取、中文表达和局部总结，却无法让固定查询链自动变成证据驱动的分析过程。

## Root-Cause Findings

### RC-1 — 模型负责“分类”，不负责理解并解决完整业务问题

`bot/router.py:1722-1730` 明确要求入口模型“只判断用户意图和抽取参数，不做分析，不查数据”，并把出口限制为六类。模型输出的核心是 `intent + brand + period + 少量固定参数`，而不是用户目标、待验证命题、所需证据、子问题和完成标准。

影响：

- 一个同时包含大盘、品牌、竞品、原因和媒体信号的问题，会被压缩成某个预定义 intent，而不是保留为多个待完成分析任务。
- 换更强模型主要提高“分得更准、说得更像人”，不会改变后面的固定执行链。
- 用户明确提出的多个子问题没有一份独立任务清单可用于检查是否全部回答。

对应 spec 缺口：FR-002、FR-005、FR-009、FR-014、SC-005。

### RC-2 — 路由承担了过多产品语义，且 V1、V2、规则、状态恢复同时存在

提交快照中的 `bot/router.py` 共 2,309 行；`bot/app.py` 中有 44 处 `route_result.type` 引用。主入口 `bot/router.py:1963-2065` 在语义分类前后依次处理 meta、集合追问、任务恢复、机会点、targeted route、V2 eligibility、实体解析和多种 pending state。V2 默认关闭，V1 仍是兼容回退。

影响：

- “用户想解决什么”被分散在正则优先级、开关、pending state 和兼容分支中，新增自然表达容易撞到旧分支。
- 路由正确只保证进入某条 chain，不保证 chain 能回答用户的完整问题。
- 当前路由调试是必要工作，但即使路由达到 100% 正确，固定分析链和洞察层的缺口仍然存在。

对应 spec 缺口：FR-003、FR-014、FR-015、SC-001、SC-002、SC-008。

### RC-3 — 模板是固定执行终点，不是可组合的分析方法

`bot/chains/default_chain.py:14-30` 用固定启发式选择下钻品类：先保留份额不低于 3% 的品类，再从接近最大份额的品类中选择；`bot/chains/default_chain.py:81-108` 随后固定执行系列、Top SKU、渠道和质检。`bot/formatter.py:1-3` 也明确写着“固定结构报告生成”，顺序固定为整体生意、品类、系列/链接、Key Driver。

这不是根据用户问题和实际证据选择分析路径。例如：

- 用户问“下滑主要来自哪里”，系统仍可能选择规模最大的核心品类，而不是最大负向增长贡献。
- 用户只问一个明确问题，仍可能得到大量不相关章节。
- 用户问一个宽泛问题时，系统没有“先筛查所有相关维度，再按异常继续下钻，证据充分后停止”的循环。

对应 spec 缺口：FR-004、FR-005、FR-008、FR-022、SC-005。

### RC-4 — 所谓联合分析实际上是报告拼接，没有跨域解释

`bot/chains/brand_business_investment_chain.py:50-63` 并行运行一个电商模板和一个 BET 模板；`bot/chains/brand_business_investment_chain.py:69-81` 只把两份 Markdown 依次放入“第一部分”和“第二部分”后连接起来。

缺少的分析动作包括：

- 对齐并比较生意与媒体的实际覆盖期间；
- 识别同步、领先、滞后和背离；
- 判断哪些变化值得联合解释；
- 给出替代解释及进一步验证要求；
- 形成一个回答原始问题的统一结论。

因此即使两份子报告都正确，用户仍需要自己完成真正的综合分析。

对应 spec 缺口：User Story 3、FR-009、FR-010、FR-016、SC-005、SC-006。

### RC-5 — “洞察”被实现为安全的事实改写，而不是证据支持的业务推理

安全边界本身是正确的，但当前实现把安全与保守绑定得过紧：

- `bot/market_formatter.py:110-131` 的“值得学习”基本等于找最大正向平台增量和最大正向商品增量，仍是事实摘要，没有业务含义、风险、行动方向或验证建议。
- `bot/opportunity_insight.py:115-150` 只允许正份额变化或正增长的候选进入机会列表，无法同时发现拖累、风险、背离和反例。
- `bot/opportunity_insight.py:225-280` 给模型的候选信息只有候选 ID、维度、名称和排序提示，不包含完整数值、跨维度关系或外部证据；模型只能从预筛候选中排序并写一句不含数字的理由。
- `bot/opportunity_insight.py:205-218` 的降级文案固定为“加大资源投入”“优先巩固”“复制打法”等通用表达。
- `bot/data/narrative_config.json:5-6` 与 Formatter 的黑名单防止强因果是合理的，但缺少对“事实—推断—假设—验证”的正向表达协议。

这解释了为什么更强模型仍可能显得“不聪明”：模型既看不到充分证据，也没有权限构建新的解释，只能润色预先决定的结论。

对应 spec 缺口：FR-010、FR-012、FR-013、SC-004、SC-006。

### RC-6 — 复杂问题增加确认步骤，但确认后仍进入固定 recipe

`bot/router.py:953-994` 对品牌生意 + BET、Top N + 原因/打法等问题进入 preflight；如果部分新执行开关未开启，就先要求用户确认。`docs/agent_plan_layer_runtime.md:6-15` 显示 Agent Plan、Executable Plan、Generated Plan 和 Unified Response 默认大多关闭或仅 shadow；`docs/agent_plan_layer_runtime.md:27-30` 说明可执行 V2 目前只激活固定 `rank_then_drill` recipe，生成计划仍关闭。

影响：

- 用户付出了额外确认成本，但分析自主性没有同比增加。
- 当信息已经充分时仍确认，会加重“难用”感。
- 当前 plan layer 更像已有模板的受控编排器，还不是按问题和证据动态决定下一步的分析循环。

对应 spec 缺口：FR-003、FR-005、SC-002。

### RC-7 — 不同职能只是用户描述，不是当前产品上下文

提交快照的会话状态里有 `function_tag`，但它代表商品功能标签（如美白、抗老），不是 Marketing、KA、Media、Business Planning、CDO 或 Trade Marketing 等用户职能。当前没有稳定的用户职能/决策视角字段，也没有在不改变事实的前提下调整业务含义和建议重点的响应规则。

影响：

- 同一份事实无法自然回答“对 Media 意味着什么”与“对 KA 意味着什么”。
- 系统更倾向输出统一模板，而不是共享事实底座上的视角适配。

对应 spec 缺口：FR-001、FR-023。

### RC-8 — 测试验证“代码是否按模板运行”，没有验证“用户问题是否被解决”

提交快照有 26 个测试文件，覆盖路由、查询、Formatter、上下文和具体报告。代码中未找到针对以下结果的评估合同：

- 是否先直接回答了用户问题；
- 是否覆盖全部子问题；
- 是否选择了最小充分证据；
- 是否形成有价值的业务含义和行动方向；
- 是否在多轮对话中让真实业务用户成功完成任务；
- GLM 与千问在同一真实问题集上的端到端差异。

所以版本可以通过大量单元测试，同时依然让真实用户觉得难用或不聪明。这不是测试数量不足，而是验收目标仍然围绕模板正确性。

对应 spec 缺口：FR-021、SC-001、SC-005、SC-006、SC-010。

| 自动选择最小充分证据 | 固定 chain 与固定下钻启发式 | Critical | 没有 evidence-led analysis loop |

## What Is Already Valuable and Should Be Preserved

当前版本并非推倒重来。以下资产是未来 Agent 的专业性基础：

- 已对齐的指标口径、排名语义、时间规则和 Segment/Category 定义；
- 结构化 Tool 与禁止任意 SQL 的执行边界；
- 品牌映射、数据覆盖、同期缺失和基期为零等质量处理；
- 天猫、抖音、京东、大盘、BET、Search、KSI/KOL 的查询能力；
- 防止无证据因果、ROI、价格和公司动作推断的护栏；
- 部分失败时继续输出其他来源的降级能力；
- 已有 Formatter 和报告模块，可继续作为展示组件。

需要改变的是这些资产的**组织方式**：从“每个模板是一条完整出口”，转为“每个模板贡献可组合的方法、证据和展示模块”。

## Root-Cause Hypothesis

> 当前版本难用、分析不够有启发性的首要根因，是系统以 route type 和固定报告为核心状态，而不是以 Business Question、Analysis Scope、Evidence、Finding、Inference、Insight 和 Completion Criteria 为核心状态。

这个假设同时解释：

- 为什么换模型后语言会改善但分析深度变化有限；
- 为什么路由 bug 很显眼，却不是唯一问题；
- 为什么已有很多专业模板，组合后仍像几份报告拼在一起；
- 为什么安全性较高，但结论经常保守、泛化或缺少下一步；
- 为什么测试通过仍不能保证用户觉得好用。

## Recommended Product Sequence

以下是产品规划顺序，不是本轮代码修改：

1. **先建立真实问题评测集**：从各职能收集代表性问题与真实多轮对话，标注核心问题、必须回答的子问题、正确口径、必要证据、不可越界结论和优秀答案特征。把 backup + 千问、backup + GLM 5.2、后续架构放在同一题集盲评。
2. **建立 Business Question 与完成合同**：入口保留用户目标、子问题、决策视角和完成标准；route 只决定能力边界，不再等同于最终报告类型。
3. **把模板拆成分析方法组件**：每个组件声明适用问题、所需输入、输出 Evidence/Finding、可继续下钻条件、停止条件和禁止推断。
4. **实现证据驱动的分析循环**：先宽度筛查，再按影响与异常选择下钻；每一步更新已回答/未回答问题和证据充分度。
5. **建立统一 synthesis contract**：跨 EC、Market、BET、Search、KSI/KOL 识别一致、背离与缺口，输出事实、推断、假设、行动方向和验证建议。
6. **最后再优化路由与模型分工**：路由负责实体和能力边界，强模型负责基于完整证据的规划与综合；用端到端评测决定 GLM 5.2 的实际收益，而不是只比较语言流畅度。

## Diagnosis Boundary

本报告没有读取线上会话日志、模型实际配置或用户满意度数据，因此不能断言某个 route 分支是线上最高频失败点，也不能量化 GLM 5.2 已带来的提升。下一步最有价值的证据是 20–50 条真实问题及对应实际回答；它们可以验证上述根因排序，并形成 spec 中 FR-021 所要求的初始评测集。
