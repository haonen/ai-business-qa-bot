# Feature Specification: 品牌电商生意分析 Agent

**Feature Branch**: `backup/server-20260831-164408`

**Created**: 2026-09-01

**Status**: Draft

**Input**: 品牌内关心生意的不同职能，希望用自然语言了解某时点或时段的电商大盘、品牌与竞品表现、涨跌原因及媒体投资等外部信号，并获得基于内部统一分析方法和数据口径的专业、灵活、充分且有启发性的分析与报告。

## Product Intent

本产品面向品牌内部需要理解和推动电商生意的人员。它不是一个要求用户记住固定命令或分析模板的报表机器人，而是一名了解品牌内部分析方法、数据口径与证据边界的生意分析伙伴。

用户只需说明自己关心的业务问题。Agent 应理解其决策意图，复用已有分析模板中的专业方法与口径，按问题动态组合必要的分析模块，并以“结论—证据—解释—启发—边界”的方式回答。模板是可组合的分析资产，而不是限制用户问题表达和答案结构的固定出口。

## Clarifications

### Session 2026-09-02

- Q: 当用户提出一个完整的业务问题时，Agent 默认应该交付什么层级的答案？ → A: 分层回答：直接结论 → 关键证据与启发 → 复杂问题或用户明确要求时生成完整报告。
- Q: 第一阶段所说的“生意之外的外部信息”应该覆盖哪些来源？ → A: 仅限已接入内部数据库的结构化数据，包括 BET、媒体投资、Social Search、KSI/KOL 等。
- Q: 你希望“有启发性的分析”具体深入到哪一层？ → A: 诊断加启发：给出有证据的业务含义、机会/风险、行动方向及验证建议。
- Q: 当用户提出宽泛的品牌表现或涨跌原因问题时，Agent 应该如何决定分析维度和下钻深度？ → A: 证据驱动：自动筛查并下钻重要维度，达到充分解释后停止。
- Q: 不同业务职能是否应该看到不同的分析重点？ → A: 所有职能共享相同事实、口径和核心结论；根据用户问题和已知职能调整解释重点、启发与后续建议，不要求用户先选择职能。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 判断大盘发生了什么 (Priority: P1)

市场、业务规划、CDO、KA 或 Trade Marketing 用户希望了解某个时点或时段的电商大盘涨跌、平台结构变化，以及哪些品牌引领或拖累变化，从而快速建立市场全貌。

**Why this priority**: 大盘判断是品牌分析和竞品分析的共同起点，错误的范围、排名口径或增长贡献会直接误导后续决策。

**Independent Test**: 给出一个包含时间范围、市场范围和“谁在引领涨跌”的自然语言问题；仅依靠本故事即可返回范围明确、数字可追溯、品牌贡献可解释的答案。

**Acceptance Scenarios**:

1. **Given** 用户给出明确期间和市场范围，**When** 用户询问大盘涨跌，**Then** Agent 先直接说明整体方向和幅度，再展示平台或月份结构及主要品牌贡献。
2. **Given** 用户使用“Top 品牌”“增长最多”“增速最快”等不同表述，**When** Agent 排名，**Then** 分别使用规模、增长额、增长率的对应口径，并在答案中明确口径。
3. **Given** 一个品牌同期基数为零或数据不完整，**When** Agent 生成排名和结论，**Then** 不把不可比品牌混入同比排名，并清楚说明数据状态。

---

### User Story 2 - 诊断本品牌或竞品为何涨跌 (Priority: P1)

用户希望了解自己的品牌或竞品在指定期间的生意表现，并继续追问增长或下滑来自哪里，包括平台、品类、渠道、系列、商品、月份节奏和其他已有业务维度。

**Why this priority**: 用户需要的不只是结果数字，而是能够定位增长来源、拖累和下一步验证方向的诊断。

**Independent Test**: 给出一个品牌、期间和“表现如何/为什么涨跌”的问题；Agent 能围绕该问题动态选择必要维度，形成从总览到关键驱动的证据链，而不是机械输出所有模板章节。

**Acceptance Scenarios**:

1. **Given** 用户询问品牌表现，**When** Agent 回答，**Then** 先给出直接结论，并用对结论最重要的维度解释规模、同比、增长额和结构变化。
2. **Given** 用户询问“为什么增长/下滑”，**When** 数据只支持观察性分解，**Then** Agent 将平台、品类、渠道、系列、商品或节奏称为增长来源、伴随信号或待验证假设，不宣称未经验证的因果。
3. **Given** 用户追问上一轮中的品牌、排名或维度，**When** 使用“它”“第一个”“这个品类”等自然表达，**Then** Agent 延续已确认的品牌、期间和范围，仅在存在会改变结论的歧义时追问。
4. **Given** 用户的问题只需少数分析模块即可回答，**When** 生成答案，**Then** Agent 不强制输出无关的完整模板。
5. **Given** 用户只提出宽泛的品牌表现或涨跌原因问题，**When** Agent 自主分析，**Then** 先筛查相关维度，再按生意影响和异常程度下钻，证据足以回答核心问题后停止，并说明重点选择依据。

---

### User Story 3 - 联合生意与外部信号形成解释 (Priority: P1)

Media、Marketing、CDO、业务规划等用户希望在生意数据之外，结合品牌可用的媒体投资、搜索、KOL 或其他外部信息，理解时间和结构上的相关变化并寻找可验证的解释线索。

**Why this priority**: 单看 GMV 只能说明发生了什么；跨域证据是形成更有启发性的业务假设和下一步动作的关键。

**Independent Test**: 对一个同时询问生意和媒体投资的问题，Agent 能在各数据源覆盖范围内对齐品牌、时间和粒度，指出一致、背离和数据缺口，并避免把相关性写成因果或 ROI。

**Acceptance Scenarios**:

1. **Given** 生意与外部数据期间可对齐，**When** 用户要求联合解读，**Then** Agent 并列展示关键变化，指出同步、领先、滞后或背离的观察性信号。
2. **Given** 不同数据源的最新可用月份不同，**When** Agent 联合分析，**Then** 明确每项证据的实际覆盖范围，不通过静默裁剪制造同期间假象。
3. **Given** 现有数据无法验证媒体导致生意变化，**When** 用户询问原因或投入效果，**Then** Agent 明确区分“可由数据支持的事实”“基于事实的推断”和“仍需补充证据的假设”。
4. **Given** 某个外部数据源缺失，**When** 其他证据仍可用，**Then** Agent 继续完成可支持的分析，并说明缺口对结论的影响。

---

### User Story 4 - 获得面向决策的启发与下一步 (Priority: P2)

用户希望 Agent 不止复述表格，还能总结最值得关注的机会、风险、异常和下一步分析方向，帮助其决定接下来查看什么、验证什么或与谁讨论什么。

**Why this priority**: 启发性是专业分析与自动报表的核心差别，但必须建立在可追溯证据和清晰推理边界上。

**Independent Test**: 给出一组包含正负驱动、结构变化和数据缺口的业务证据；Agent 能按业务重要性排序，产出少量非泛化、可追溯、可继续验证的启发。

**Acceptance Scenarios**:

1. **Given** 存在多个变化信号，**When** Agent 总结启发，**Then** 按生意影响、变化强度和证据可信度排序，而不是按模板章节顺序罗列。
2. **Given** 证据支持某个业务机会或风险方向，**When** Agent 输出启发，**Then** 说明业务含义、可考虑的行动方向及其依据，并提供验证建议。
3. **Given** 一个建议无法由现有证据直接推出，**When** Agent 输出该建议，**Then** 将其表述为待验证假设，并说明所需补充证据，不把建议描述为确定有效的策略。
4. **Given** 没有足够证据形成行动建议，**When** Agent 结束回答，**Then** 诚实说明暂不能判断，并提供最有价值的下一步分析问题，而不是生成通用建议。

---

### User Story 5 - 用自然语言完成多轮分析 (Priority: P2)

不同职能用户希望以熟悉的业务语言提问、修改范围、追问细节或要求形成报告，而不需要了解底层模板名称、数据表或路由规则。

**Why this priority**: 如果用户需要学习系统内部分类才能得到正确答案，即使单个模板准确，整体产品仍然难用。

**Independent Test**: 使用包含省略、指代、范围修正和跨域追问的多轮对话；Agent 能保持任务上下文并让用户用最少轮次完成分析。

**Acceptance Scenarios**:

1. **Given** 用户提供的信息足以唯一确定分析范围，**When** Agent 接收请求，**Then** 不增加确认步骤，直接分析。
2. **Given** 缺少的信息会显著改变数据口径或结论，**When** Agent 无法安全采用默认值，**Then** 一次只追问最关键的信息，并保留用户原始问题中的其他要求。
3. **Given** 用户修正平台、期间、品牌或比较对象，**When** Agent 继续任务，**Then** 仅更新被修正的范围，不丢失其他已确认意图。
4. **Given** 用户要求报告，**When** 分析完成，**Then** 报告保留直接回答、关键证据、推理边界和后续启发，而不是仅拼接多个独立模板。

### Edge Cases

- 用户只给出模糊时间、营销节点名称或互相冲突的主分析期与对比期。
- 用户问题包含多个品牌、多个平台、多个期间或不同粒度，且无法在同一口径直接比较。
- 同一品牌在不同数据源中名称不同、存在候选匹配或某来源没有该品牌。
- 当前期或同期缺失、同期为零、数据只覆盖部分月份、不同来源更新时间不一致。
- 用户将“Top”“增长最多”“增速最高”“贡献最大”混用，或未明确排序口径。
- 用户要求解释价格、促销、投放效果、ROI、公司动作或消费者原因，但现有数据不具备相应字段或归因设计。
- 用户追问代词或序号时，上下文中存在多个合理指代对象。
- 查询或部分分析模块失败，但其他模块仍可完成。
- 结果包含异常值、疑似数据质量问题或与上一轮口径不一致。
- 用户问题超出现有数据范围；Agent 必须说明边界并建议可回答的相邻问题，不得悄悄替换成其他口径。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Agent MUST 支持品牌内部关心电商生意的 Marketing、KA、Media、Business Planning、CDO、Trade Marketing 等职能，以自然业务语言发起分析；不同职能共享相同事实、口径和核心结论，答案重点根据用户问题及已知职能调整，且不得要求用户先选择职能才能提问。
- **FR-002**: Agent MUST 从用户问题和有效会话上下文识别品牌、竞品、时间范围、比较期、市场/Segment、平台、品类、所需指标、分析深度及输出形式。
- **FR-003**: Agent MUST 仅在缺失信息会改变口径、数据选择或结论时发起澄清，并保留用户已经表达的所有有效要求。
- **FR-004**: Agent MUST 将既有分析模板中的口径、拆解顺序、阈值、禁用推断和展示规则作为可复用的分析方法，而不是要求每个用户问题固定映射到一个完整模板。
- **FR-005**: Agent MUST 根据用户的核心问题动态组合分析模块；对于宽泛问题，先筛查可用的相关维度，再按生意影响和异常程度自动下钻，优先选择能够验证或反驳关键业务判断的最小充分证据集，并在证据足以回答核心问题后停止。
- **FR-006**: Agent MUST 支持大盘趋势、品牌排名、品牌/竞品表现诊断、增长与拖累分解、跨平台分析、时间节奏分析、商品/系列/渠道下钻，以及生意与已接入内部数据库的 BET、媒体投资、Social Search、KSI/KOL 等结构化信号的联合解读。
- **FR-007**: Agent MUST 对所有排名显式区分规模、增长额、增长率和增长贡献，并在结果中展示使用的排序口径。
- **FR-008**: Agent MUST 默认采用分层回答：先直接回应用户最关心的问题，再提供关键证据与启发；仅在问题复杂或用户明确要求时生成完整报告，不得用流程说明或长篇数据口径替代直接回答。
- **FR-009**: Agent MUST 形成跨模块的统一叙事，说明“发生了什么、主要由哪些可观察维度构成、哪些外部信号一致或背离、意味着什么、还需要验证什么”，不得仅拼接彼此独立的章节。
- **FR-010**: Agent MUST 将输出中的重要陈述标识为可验证事实、基于事实的推断或待验证假设，并确保所有数字、实体、排名和比较均可追溯到本次使用的证据。
- **FR-011**: Agent MUST 避免未经证据支持的因果、ROI、公司策略、人群动机、价格优势、促销效果和行业判断；当用户要求此类结论时，说明现有证据能支持到哪一层。
- **FR-012**: Agent MUST 根据生意影响、变化强度、证据完整性和与用户问题的相关性，对驱动、风险、机会和异常进行排序，并解释它们对当前业务问题意味着什么。
- **FR-013**: Agent MUST 在证据支持时给出业务含义、机会/风险判断、可考虑的行动方向及验证建议；行动方向必须关联具体证据并标明其属于推断或假设，不得承诺策略效果。证据不足时提供具体的验证问题或所需补充数据，不输出空泛建议。
- **FR-014**: Agent MUST 在多轮对话中维持任务级上下文，包括原始业务问题、已确认范围、已用证据、关键结论、未回答部分和用户后续修正。
- **FR-015**: Agent MUST 支持用户从大盘进入品牌、从品牌进入平台/品类/渠道/系列/商品、从生意进入媒体等外部证据，也支持返回上层重新比较，而无需重新描述整个问题。
- **FR-016**: Agent MUST 在不同来源或分析模块的期间、品牌映射、粒度或数据覆盖不一致时显式说明，并阻止不可比数据被合并成单一结论。
- **FR-017**: Agent MUST 在部分数据或模块失败时保留其余可用分析，说明失败影响；只有核心问题无法获得任何有效证据时才停止。
- **FR-018**: Agent MUST 对超出支持范围的问题给出清晰边界和最接近的可回答路径，不得静默忽略用户条件或自动改用其他口径。
- **FR-019**: Agent MUST 同时支持适合即时决策的分层对话答案和适合分享的完整分析报告；完整报告不是所有请求的默认输出，两者使用相同证据与结论，报告可增加明细但不得改变核心判断。
- **FR-020**: Agent MUST 记录足以复核一次回答的分析范围、所用模块、证据来源、数据覆盖、关键派生口径、未支持部分及降级情况。
- **FR-021**: 产品团队 MUST 维护覆盖主要用户故事、常见自然语言变体、多轮上下文、口径边界和洞察质量的代表性问题集，用于比较版本质量。
- **FR-022**: Agent MUST 能够说明本次筛查了哪些可用维度、为何重点展开当前驱动或异常，以及哪些维度因影响较小、证据不足或与问题无关而未继续下钻。
- **FR-023**: 当用户问题或已有上下文能识别其决策视角时，Agent MUST 在不改变事实和核心结论的前提下调整业务含义、机会/风险、行动方向和后续问题的表达重点；无法识别职能时按问题本身回答，不额外追问职能。

### Analysis Response Contract

每次实质性业务分析应按用户问题裁剪，但必须能回答以下内容：

1. **直接答案**：用业务语言先回答用户最想知道的判断。
2. **分析范围**：品牌/市场、期间、对比期、平台和关键口径。
3. **关键证据**：只展示支撑判断所需的数字、表格或变化信号。
4. **解释链路**：按影响排序说明可观察的增长来源、拖累、结构变化和跨域一致/背离。
5. **业务启发**：给出有证据的业务含义、机会/风险、可考虑的行动方向及下一步验证方法，并标明事实、推断与假设的边界。
6. **边界与缺口**：明确数据不可比、缺失和无法验证的因果部分。

### Key Entities

- **Business Question**: 用户真正要做的业务判断；包含原始表述、决策意图、分析对象、核心问题和期望输出。
- **Analysis Scope**: 已确认的品牌/市场、主期间、比较期、平台、Segment、品类、指标、排名口径和分析深度。
- **Analysis Method**: 来自内部模板的可复用分析逻辑，包括适用条件、所需证据、口径、计算、阈值、禁用推断和输出义务。
- **Evidence Item**: 支持某项陈述的数据证据；包含来源、覆盖范围、粒度、实体、指标、值、比较状态和质量状态。
- **Finding**: 由一项或多项证据支持的业务发现；包含方向、影响大小、优先级和证据引用。
- **Inference**: 基于发现形成但不是直接数据事实的解释；包含可信度、替代解释和验证要求。
- **Insight**: 与用户决策相关的含义、机会、风险或下一步；必须关联 Finding 或 Inference。
- **Analysis Task Context**: 跨轮保存的原始目标、已确认范围、已完成/待完成分析、关键发现、指代对象和用户修正。
- **Analysis Report**: 面向分享的完整输出，由统一的直接答案、证据链、解释、启发和边界组成。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在经业务团队标注的代表性问题集中，至少 90% 的请求首次进入正确的分析范围，且不会因内部模板分类错误而要求用户重述问题。
- **SC-002**: 当用户已提供足够范围时，至少 90% 的请求无需额外确认即可开始分析；需要确认时，平均不超过 1 个澄清回合。
- **SC-003**: 100% 的关键数字、排名和实体结论能够追溯到本次分析证据及明确口径。
- **SC-004**: 100% 的因果、ROI、策略、人群或价格相关结论遵守证据边界；无证据时明确标为推断、假设或无法判断。
- **SC-005**: 对包含多个分析维度的代表性问题，至少 85% 的答案覆盖用户明确提出的全部子问题，且不以无关模板章节稀释核心回答。
- **SC-006**: 业务评审者在盲评中至少 80% 的答案被评为“先回答了问题”“分析逻辑专业”“结论有证据”“提供了有价值的下一步”四项均达标。
- **SC-007**: 在部分数据源缺失或模块失败的测试中，至少 95% 的请求仍返回可用的剩余分析，并准确说明缺口影响。
- **SC-008**: 在多轮代表性对话中，至少 90% 的指代、范围修改和继续下钻能保持正确任务上下文，且不丢失用户原始问题中的未完成部分。
- **SC-009**: 对同一问题生成的即时答案与分享报告，100% 保持核心结论、数字和口径一致。
- **SC-010**: 与当前线上基线相比，业务用户完成“得到一个可用于讨论或决策的答案”的成功率提高至少 30%，平均无效交互回合减少至少 40%。

## Assumptions

- 第一阶段面向品牌内部已获授权的用户，不在本 feature 中重新定义身份认证与数据权限体系。
- 第一阶段以仓库现有电商生意、市场、BET、媒体投资、Social Search、KSI/KOL 等已接入内部数据库的结构化数据为事实基础；新增数据源属于后续范围，但当前设计必须能表达数据缺口并允许未来扩展。
- 内部已有分析模板及口径经过业务对齐，应保留其正确性；本次重构重点是让这些方法可组合、可选择、可追溯，而不是推翻业务口径。
- 默认比较方式为同比；只有用户明确要求或业务问题需要时才加入环比、时段对比或其他比较。
- 默认使用中文业务表达，保留必要的内部英文指标和缩写，并在首次出现时给出清晰含义。
- “聪明”被定义为正确理解任务、选择最小充分证据、形成跨模块解释、区分事实与推断并提出可验证启发，而不是更自由地生成未经证据支持的故事。

## Out of Scope

- 自动做出预算分配、投放、选品、定价或商业承诺。
- 在缺少归因设计时计算或宣称媒体投入对 GMV 的因果效果或 ROI。
- 使用仓库未接入或用户无权访问的外部数据作为事实。
- 检索用户上传文档、内部研究报告或公开互联网中的竞品活动、新闻、社媒和行业信息；这些来源不属于第一阶段验收范围。
- 要求用户学习模板名称、内部路由类型、数据表名称或技术实现才能提问。
- 以更换单一模型作为满足本 feature 的充分条件；模型质量是影响因素，但验收以完整分析行为为准。
